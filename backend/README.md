# LifeCycle API

Модульный Rust API на Axum. PostgreSQL — единственный источник сохраняемых данных; Redis предназначен для краткоживущих данных, Garage — для приватных файлов. API публикуется через тот же origin, что и frontend; CORS не включён.

## Упражнения и тренировки (этап 5)

Миграция `0005_workouts.sql` добавляет библиотеку упражнений, планы и сессии. Существующие миграции и данные этапов 1–4 сохраняются. Все маршруты требуют сессии; мутации также требуют корректный Origin. Чужие UUID возвращают 404 (непринадлежащие изображения и упражнения в форме — 400). Новых зависимостей нет.

### Библиотека и конструктор

- `GET /api/exercises?q=...`, `POST /api/exercises`, `GET|PUT|DELETE /api/exercises/{id}`.
- `GET /api/workouts?q=...&tag=...`, `POST /api/workouts`, `GET|PUT|DELETE /api/workouts/{id}`.
- Ответ записи: `{id,data,created_at,updated_at}`; списки и чтение содержат только существующие объекты. DELETE физически удаляет объект, сохраняя результаты сессий. POST создания возвращает 201, DELETE — 204.

`Exercise`: `{title,kind,description,images,sources}`. Название 1–200 символов, Markdown до 200000. Виды: `repetitions`, `duration`, `repetitions_duration`. `images` — до трёх уникальных UUID собственных загруженных через `/api/media` изображений. `sources` — до 10 HTTP(S)-ссылок по 2000 символов без credentials. Внешние изображения через Markdown не загружаются. Тип и удаление упражнения блокируются с 409, пока оно используется активным планом; название/технику/иллюстрации можно менять. Начатая сессия сохраняет прежнюю технику.

`Workout`: `{title,description,tags,rounds}`. Текст/теги ограничены как у задач. 1–20 упорядоченных кругов. Круг: `{id,title,repeat,rest_seconds,exercises}`; repeat 1–20, отдых 0–3600 секунд, 1–50 упражнений. Включение упражнения: `{id,exercise_id,repetitions,duration_seconds,rest_seconds,progression,intensity?}`. Необязательная intensity — описание интенсивности до 200 символов, по умолчанию пустое; сохраняется в snapshot шага. UUID кругов/включений уникальны внутри плана. Можно повторно включать одно упражнение с разной нагрузкой. Порядок массивов задаёт выполнение.

Для `repetitions` — 1–10000 повторений и нулевое время; для `duration` — нулевые повторения и 1–86400 секунд; для `repetitions_duration` — оба значения положительны, таймер равен их произведению (не более суток). Отдых включения — 0–3600 секунд. Сначала выполняются все включения круга и их отдых, затем отдых круга, затем следующий повтор/круг. Все завершающие отдыхи убираются. До 500 фактических шагов; верхняя оценка суммарного времени при максимальных начальных/целевых значениях с отдыхом — до суток. Снимок при запуске ограничен 4 MiB; большие описания в многократно повторяемых планах требуют сокращения или разделения плана.

`progression` — null либо `{start_date,days,target_repetitions,target_duration_seconds}`. Days 1–3650, целевые значения соответствуют виду упражнения. Сервер рассчитывает каждое значение отдельно: `initial + floor((target-initial) * clamp(elapsed_days,0,days) / days)`. До начала действует initial, после срока — target; снижение нагрузки поддерживается. Elapsed — календарные дни, не интервалы по 24 часа. При обычном запуске используется дата профиля, при запуске из привычки — ключ даты её расписания. Это пользовательские цели, без автоматических рекомендаций физической нагрузки.

### Выполнение и таймеры

- `POST /api/workout-sessions` с `{workout_id,habit_id?,date?}` запускает сессию; habit_id/date передаются вместе либо отсутствуют. Ответ 200. Для привычки разрешены только существующие текущие/прошлые появления её версий расписания, с совпадающим workout_id.
- Одна running/paused сессия на аккаунт. Повтор такого же запуска возвращает её, другой запуск — 409. Завершённое полное выполнение той же habit/date возвращается повторно без нового события. После partial/cancelled разрешена новая попытка.
- `GET /api/workout-sessions/active` возвращает сессию либо null; `GET /api/workout-sessions/{id}` возвращает подробности, в том числе после удаления плана.
- `GET /api/workout-sessions?workout_id=...&before=ISO_TIMESTAMP` возвращает до 50 кратких записей `{id,workout_id,title,date,status,confirmed_steps,habit_completed,started_at,ended_at}`; before исключающий, сортировка от новых к старым. Подробный snapshot не дублируется в списке.
- `POST /api/workout-sessions/{id}/{action}` с `{revision,actual_repetitions?,note?}`. Actions: `pause`, `resume`, `next`, `skip`, `cancel`, `note`. Каждая команда увеличивает revision; устаревшая команда возвращает 409 `stale_workout`, повторное продвижение исключено. Мутации сериализованы на аккаунт и блокируют строку сессии.
- Session содержит snapshot `{plan,date,steps}`, status, step_index, elapsed_seconds, segment_started_at, results, note, revision и признаки связи с привычкой. Шаг хранит снимок упражнения, круг/повтор, рассчитанные repetitions, seconds_per_repetition и duration_seconds. Results хранят индекс шага, completed/skipped, фактические повторения, серверное время и длительность.
- Таймер работает на сервере, пауза замораживает накопленное время; reload/закрытие вкладки не сбрасывают сессию. Истечение таймера не подтверждает фактическое выполнение автоматически. Next разрешён только в running и после истечения времени шага. Для обычных повторений время не ограничено. Actual_repetitions — 0–10000, по умолчанию плановое число; при меньшем результате сессия станет partial. Skip разрешён в running/paused; пропуск отдыха не считается пропуском упражнения. Cancel сохраняет подтверждённые шаги и время текущего шага, автоматически привычку не меняет.
- Все упражнения подтверждены без пропусков и достигнуты плановые повторения — completed; иначе после последнего шага partial. Заметка Markdown до 200000 символов сохраняется командой note, включая завершённую сессию. Снимки плана и результатов не редактируются.

### Связь с привычками, Today и календарём

`HabitConfig` дополнен необязательным `workout_id: UUID|null`, прежние JSON и snapshots совместимы. Привычка с тренировкой не может иметь sub_habits. Расписание и напоминания остаются в общем Habit/Task/Schedule; отдельного дублирующего движка тренировок нет. Для разных планов по дням недели создаются отдельные недельные привычки. Today/календарь получают идентификатор в snapshot привычки и запускают соответствующую сессию с исходным ключом даты, независимо от зоны профиля.

Полное завершение сессии и отметка соответствующего появления привычки записываются в одной транзакции, через общую функцию отметок привычек; её статистика и Today сразу используют реальный результат. Частичное выполнение/отмена привычку не завершают. Если привычка удалена, отвязана от плана или пользователь явно отменил/пропустил её появление, сессия сохраняется без изменения отметки (`habit_completed=false`). Ручная заметка к отметке сохраняется. Существующие сохранённые snapshots продолжают использовать исходную связь. Удаление плана запрещено, пока на него ссылаются активные текущие привычки: сначала отвязать или удалить их. Прошлые результаты и начатые сессии сохраняются.

Создание/изменение/удаление упражнений и планов, запуск и команды сессий атомарно пишут реальные `activity_events`; эти события используются аналитикой этапа 7. Проверка: `python3 scripts/workouts_smoke.py`, дополнительно Chromium `frontend/e2e/workouts.spec.ts`.

## Конфигурация

Обязательны `DATABASE_URL`, `REDIS_URL`, `APP_PUBLIC_URL`, `S3_ENDPOINT`, `S3_BUCKET`, `S3_REGION`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`. `APP_BIND` по умолчанию `0.0.0.0:8080`. `APP_PUBLIC_URL` — внешний HTTP(S) origin; `S3_ENDPOINT` — HTTP(S) origin Garage без пути и credentials. Секреты не возвращаются в API и не записываются в журналы. Переменные передаются средой, приложение не загружает `.env` само.

При запуске SQLx применяет версионированные миграции; при ошибке подключения или миграции процесс завершается с кодом 1. Доменная схема `app` создаётся миграцией этапа 1; таблицы функций добавляются на соответствующих этапах. Существующие миграции нельзя менять после применения.

## HTTP контракт

- `GET /api/health/live`: HTTP 200, `{"status":"ok"}`. Процесс обслуживает HTTP независимо от доступности инфраструктуры.
- `GET /api/health/ready`: HTTP 200, `{"status":"ready","checks":{"postgres":"ok","redis":"ok","garage":"ok"}}`.
- При недоступности зависимости readiness возвращает HTTP 503, `status: "unavailable"`, и статус `"unavailable"` соответствующей проверки. PostgreSQL проверяется `SELECT 1`, Redis — `PING`, Garage — подписанным S3 ListObjectsV2 с лимитом 1. Объекты и подробности внутренних ошибок не раскрываются. Проверки выполняются параллельно, каждая ограничена 3 секундами.
- Неизвестный маршрут: HTTP 404, `{"error":{"code":"not_found","message":"Route not found"}}`.

Ответы содержат `Cache-Control: no-store`, `X-Content-Type-Options: nosniff` и `Referrer-Policy: no-referrer`. Размер тела ограничен 1 MiB, для загрузки изображений — 8 MiB; запрос — 10 секундами. TLS завершается на reverse proxy. SIGTERM и Ctrl+C инициируют graceful shutdown.

## Команды

Из `backend`: `cargo fmt --check`, `cargo clippy --locked --all-targets -- -D warnings`, `cargo test --locked`, `cargo run --locked`.

Тесты проверяют валидацию конфигурации, отсутствие секретов в ошибках, liveness и реальные отказы подключения при readiness. Успешный путь всех зависимостей проверяется отдельно на запущенном Compose-стеке; unit-тесты не подменяют эту проверку.

Использованы [Axum](https://docs.rs/axum/latest/axum/), [SQLx](https://docs.rs/sqlx/latest/sqlx/), [Redis](https://docs.rs/redis/latest/redis/) и [rust-s3](https://docs.rs/rust-s3/latest/s3/). Lockfile фиксирует фактически проверенные версии.

## Идентификация, профиль и настройки (этап 2)

Дополнительные обязательные переменные: `AUTH_CODE_SECRET` (минимум 32 случайных байта), `DATA_ENCRYPTION_KEY` (base64, ровно 32 байта), `SMTP_HOST`, `SMTP_PORT`, `SMTP_TLS` (`tls`, `starttls`, `none`), `SMTP_FROM`. Опционально `SMTP_USERNAME` и `SMTP_PASSWORD` задаются вместе. `none` разрешён только для localhost/Mailpit при HTTP-конфигурации приложения. Для внешней почты используйте проверяемый TLS либо обязательный STARTTLS. Локальный Mailpit принимает настоящие SMTP-письма без отправки за пределы стенда; его UI не является частью публичного приложения.

`TRUST_PROXY=false` по умолчанию: лимиты привязаны к TCP peer IP. `true` разрешает доверять единственному `X-Real-IP`, который reverse proxy обязан перезаписывать адресом клиента. В этом режиме API должен быть доступен только из приватной сети proxy; прямой публичный доступ к API недопустим. Произвольный `X-Forwarded-For` не используется.

- `POST /api/auth/request-code` с `{"email":"person@example.org"}`: HTTP 202, `{"message":"Verification code sent"}`. Адрес очищается от внешних пробелов и приводится к нижнему регистру; регистрация и вход используют один поток. Код — криптографически случайные 6 цифр, действует 10 минут; повторная отправка не чаще раза в 60 секунд. Не более 10 запросов на адрес и 100 на клиентский IP в час. Redis хранит HMAC адреса и кода, а не email или код в открытом виде. Почтовая ошибка возвращает 503 `mail_unavailable`; фиктивный успешный ответ не выдаётся.
- `POST /api/auth/verify-code` с `{"email":"person@example.org","code":"123456"}`: HTTP 200, `{"user":{"id":"UUID","email":"person@example.org"}}`. Неправильный, истёкший либо уже использованный код: 401 `invalid_code`. Максимум 5 проверок на адрес за 10 минут, повторная отправка не сбрасывает счётчик; клиентский IP ограничен 100 проверками в час. Проверка и удаление кода атомарны через Lua, поэтому параллельная проверка имеет только одного победителя.
- `GET /api/auth/me`: такой же объект пользователя; без действующей сессии 401 `unauthenticated`.
- `POST /api/auth/logout`: HTTP 204, сессия отозвана в БД, cookie очищена. Повторный logout безопасен.

Сессия — 256 случайных битов в cookie `lifecycle_session`; в PostgreSQL хранится только SHA-256 токена. Cookie: `HttpOnly; SameSite=Lax; Path=/; Max-Age=2592000`, а при HTTPS дополнительно `Secure`. Один месяц определён как 30 суток без скользящего продления. Коды и токены не выдаются в JSON и не логируются. Все мутации требуют `Origin` и проверяются против origin из `APP_PUBLIC_URL` (включая порт), несовпадение или `Sec-Fetch-Site: cross-site` возвращает 403 `csrf_failed`. CLI-клиенты также обязаны передавать корректный Origin; отсутствие заголовка возвращает 403. JSON-мутации принимают только JSON.

`GET /api/profile` и `PUT /api/profile` возвращают непосредственно объект профиля; PUT полностью заменяет профиль. Неизвестные поля запрещены. Поля:

- `nickname`, `name`: строки до 80 символов.
- `gender`: `unspecified`, `female`, `male`, `other`.
- `birth_date`: ISO-дата либо null, между 1900-01-01 и сегодняшней датой UTC.
- `birth_country`, `residence_country`, `eye_color`, `hair_color`, `skin_color`, `breast_size`: строки до 100 символов.
- `height_cm`: число 1–300 либо null; `weight_kg`: 1–700 либо null.
- `arms_count`, `legs_count`: целые 0–10 либо null.
- `colleagues_count`, `friends_count`, `acquaintances_count`: целые 0–1000000 либо null.
- `conditions`, `daily_medications`, `past_medications`, `surgeries`: массивы строк, максимум 100 записей по 500 символов.
- `has_family`, `has_partner`, `pregnant`: bool либо null.
- `penis_length_cm`, `penis_width_cm`: числа 0–100 либо null.

Все поля анкеты добровольные: строки по умолчанию пустые, массивы пустые, числа/даты/логические значения null, пол `unspecified`. Пол не определяет доступность других полей. Границы значений — техническая валидация, не медицинские нормы. Профиль хранится полностью зашифрованным AES-256-GCM с новым nonce для каждого сохранения; аутентифицированный контекст содержит user ID, так что подмена зашифрованного профиля между пользователями обнаруживается. Потеря ключа делает анкеты нечитаемыми: ключ необходимо резервировать отдельно от БД; ротация требует отдельной миграции шифротекста.

`GET /api/settings`, `PUT /api/settings`: непосредственно объект `{"timezone":"UTC","time_format":"24h","language":"ru","theme":"system","reminders_enabled":false,"reminder_minutes_before":10,"week_starts_on":"monday","pomodoro_work_minutes":25,"pomodoro_break_minutes":5}`. Часовой пояс — валидный IANA; язык пока только `ru`; тема `system|light|dark`; начало недели `monday|sunday`; напоминание 0–1440 минут; длительности pomodoro 1–180 минут. Pomodoro использует эти длительности при запуске новой сессии; активный таймер сохраняет исходную длительность. Напоминания привычек используют эти настройки на этапе 4. Доступ к данным ограничен ID текущей сессии, передать чужой user ID в API нельзя. Ошибки: 400 `validation_error`, 429 `rate_limited` с Retry-After по оставшемуся TTL ограничителя, 500 `internal_error` либо 503 `service_unavailable`; внутренние детали не раскрываются.

Дополнительные библиотеки обоснованы функциями: lettre — SMTP и TLS, aes-gcm — стандартное authenticated encryption, rand — ОС-генератор случайности, sha2/hmac — токены и OTP, base64/hex — транспорт секретов, chrono/chrono-tz — валидация дат и IANA timezone, uuid — идентификаторы пользователей.

В этапе 9 к настройкам добавлен `time_format`: `24h` (по умолчанию) или `12h`. GET всегда возвращает поле; PUT валидирует его. Ранее сохранённые JSON и запросы без поля получают `24h` через serde default, поэтому новая миграция не нужна. Формат влияет на отображение времени; UTC-моменты, даты отметок и расписания сохраняются.

## Основные данные и планирование (этап 3)

Все маршруты ниже требуют сессию, мутации также требуют корректный `Origin`. UUID ресурсов всегда проверяется вместе с владельцем: чужой либо удалённый ресурс возвращает 404. PUT полностью заменяет редактируемые поля; неизвестные поля JSON запрещены. DELETE физически удаляет сущность. Существующие миграции 0001–0003 сохраняются без переписывания.

### Заметки и папки

- `GET|POST /api/notes/folders`, `GET|PUT|DELETE /api/notes/folders/{id}`. Вход `{name,color}`: непустое имя до 100 символов, цвет `#RRGGBB`. Ответ дополнительно содержит `id,created_at,updated_at`. Удаление папки переносит её заметки в корень, сохраняя содержимое.
- `GET|POST /api/notes`, `GET|PUT|DELETE /api/notes/{id}`. Вход `{title,content,tags,color,folder_id}`: название 1–200 символов, исходный Markdown до 200000 символов, максимум 30 тегов по 1–64 символа, цвет `#RRGGBB`, UUID активной собственной папки либо null. Ответ дополнительно содержит `id,created_at,updated_at`.
- Список заметок принимает `q` (поиск подстроки без учёта регистра в названии и содержимом), `folder_id` и `tag` (точное совпадение тега). Пустой `q` допустим, максимальная длина 200 символов. Ответ — массив, сортировка по последнему изменению.

Markdown хранится как исходный текст; frontend отображает GFM без исполнения сырого HTML. Загруженные изображения используют приватные ссылки `/api/media/{id}`.

### Задачи, подзадачи и расписания

- `GET|POST /api/tasks`, `GET|PUT|DELETE /api/tasks/{id}`. Вход `{title,description,status,tags,color,priority,parent_id,due_at,schedule}`. Название 1–200 символов, Markdown-описание до 200000 символов, теги/цвет как у заметки. Статусы `todo|in_progress|completed|rejected`, приоритеты `low|normal|high|urgent`. Родитель — другая активная собственная задача либо null; циклические иерархии запрещены. Удаление родителя сохраняет подзадачи, перемещая их в корень.
- `due_at` — ISO-момент с часовым поясом либо null. `schedule` — объект расписания либо null. Дедлайн и плановое время независимы; у задачи без расписания дедлайн определяет её день в календаре. Задача без расписания и дедлайна остаётся в общем списке.
- Ответ дополнительно содержит `id,source_kind,source_id,created_at,updated_at`; для ручных задач `source_kind=manual`, `source_id=null`. Эти поля формирует backend.
- Список принимает `q,status,tag,from,to`. Поиск `q` работает по названию/описанию, `tag` — по точному совпадению. Даты включительны, обе границы задают диапазон максимум 366 дней; допускается одна открытая граница. Повторение включается, если хотя бы одно плановое появление попадает в диапазон; длинные интервалы и давно созданные правила поддерживаются. Даты поиска и календаря используют часовой пояс профиля.

Общая модель расписания:

```json
{"start_date":"2026-10-27","time":"09:15","timezone":"Europe/Moscow","duration_minutes":30,"recurrence":"weekly","interval_days":1,"weekdays":[1,3,5],"end_date":null}
```

`time` — `HH:MM` либо null, `timezone` — IANA, длительность 1–1440 минут. Правила `once|daily|weekly|interval`; дни недели ISO 1–7 без дубликатов, для weekly нужен хотя бы один день. `interval_days` — 1–3650 календарных дней; `end_date` включительна и не раньше начала. Интервалы считаются календарными днями в зоне расписания, сохраняя локальное время при DST. Неоднозначное время выбирает первый момент; отсутствующее переносится к ближайшей допустимой минуте, включая пропущенный календарный день. Расписание без времени задаёт задачу на день; дедлайн не превращает его в событие со временем.

### Today, календарь и история

- `GET /api/today?date=YYYY-MM-DD`: `{date,timezone,tasks}`. Без параметра выбирается сегодняшний день в зоне профиля.
- `GET /api/calendar?from=YYYY-MM-DD&to=YYYY-MM-DD`: `{from,to,timezone,occurrences}`. Обе границы обязательны и включительны, диапазон 1–366 дней.
- Появление имеет форму `{task,date,starts_at,status,editable}`. `date` — постоянный ключ даты в зоне расписания, `starts_at` — UTC-момент либо null. События со временем группируются в календаре по `starts_at` в `timezone` ответа; задачи без времени — по `date`. Поэтому задача на 28 октября 00:30 в Токио видна 27 октября в профиле UTC, но отмечается по ключу `2026-10-28`. `editable` вычисляется на выдаче Today, календаря, истории и результата отметки: true только для активной собственной задачи, дата которой соответствует действующему расписанию (либо задача не имеет расписания). Для удалённых задач и дат за пределами изменённого правила false; frontend отображает их как исторические результаты без управления статусом. Это возможность текущего ответа, она не хранится в snapshots и не изменяет исторические данные.
- `POST /api/tasks/{id}/occurrences/{date}` с `{status}` сохраняет результат конкретного появления. Дата обязана соответствовать правилу расписания. Для повторяющихся задач template.status остаётся `todo`, а результаты независимы для каждой даты. Для однократных задач статус синхронизируется с самой задачей; повторное сохранение того же результата идемпотентно. Возврат однократной задачи в `todo` через PUT также снимает отметку завершения в календаре.
- `GET /api/tasks/{id}/history`: массив сохранённых появлений по дате в обратном порядке, включая историю удалённой собственной задачи.

Результаты `completed/rejected` сохраняют снимки названия, описания, расписания и времени. Правка либо удаление шаблона не меняет эти результаты и не удаляет историю. Для `todo/in_progress` календарь показывает актуальную активную задачу и сохранённый статус; перенос или удаление отменяет её старые незавершённые появления. История остаётся доступной. Пользовательские мутации и изменения статусов атомарно записывают реальные доменные события в `app.activity_events`; аналитика этапа 7 использует эти события.

### Приватные изображения

`POST /api/media` принимает непосредственно байты PNG/JPEG/WebP с соответствующим `Content-Type`, максимум 8 MiB, и возвращает HTTP 201 `{id,url,content_type,size}`. SVG, HTML и несоответствие сигнатуры типу отклоняются. `GET /api/media/{id}` выдаёт исходные байты только владельцу с исходным MIME и `Content-Disposition: inline`. Bucket Garage остаётся приватным; внешние S3-ключи клиенту не раскрываются. Проверка сигнатуры не является перекодированием изображения. При ошибке сохранения метаданных загрузка удаляется из S3 по возможности.

### Countdown и Pomodoro

- `GET|POST /api/countdowns`, `GET|PUT|DELETE /api/countdowns/{id}`. Вход `{title,category,icon,target_date,repeat_yearly}`: название 1–200, категория 1–64, значок до 48 символов, дата между годами 1900 и 9998. Ответ дополнительно содержит `id,next_date,days_remaining,next_at,created_at,updated_at`. Ежегодное повторение использует месяц/день исходной даты; 29 февраля соответствует 28 февраля в невисокосном году. Расчёты используют текущую дату и полночь в зоне профиля.
- `GET /api/pomodoro`: активная сессия либо null. `POST /api/pomodoro` с `{task_id:null,phase:"work"}` запускает сессию, `phase=work|break`; можно привязать активную собственную задачу. Длительность берётся из настроек. Одновременно допустима одна running/paused сессия; повторный запуск возвращает 409.
- `POST /api/pomodoro/{id}/pause|resume|finish|cancel` меняет состояние сессии. Ответ содержит `id,task_id,phase,status,duration_seconds,elapsed_seconds,started_at,segment_started_at,ended_at,updated_at`. Счёт времени основан на серверных UTC-сегментах, сохраняется при перезагрузке и не увеличивается в паузе. `elapsed_seconds` в ответе уже включает активный сегмент на момент ответа; клиент добавляет только время после получения ответа. `finish` разрешён после истечения длительности, раннее завершение и недопустимые переходы возвращают 409. Истёкшая сессия остаётся активной до подтверждения завершения или отмены.

Проверка этапа 3: `python3 scripts/core_smoke.py --check-oversize --check-completion` из корня на реальном стенде (`--url`, `--origin`, `--mailpit-url` при необходимости). Она проверяет CRUD, поиск, иерархию, историю, повторения, часовые пояса, перезапуск статусов, приватный S3 и Pomodoro; не подменяет инфраструктуру mock API. `--check-completion` дополнительно ожидает истечение настоящего минутного таймера, поэтому добавляет около минуты к проверке.


## Привычки и напоминания (этап 4)

Миграция `0004_habits.sql` добавляет `tasks.habit`, `habit_versions` и `habit_reminder_receipts`, сохраняя миграции 1–3. Привычка — task template с `source_kind=habit`, `source_id=id`. Единственное появление `(user_id,task_id,date)` использует существующий движок `Schedule`, таблицу `task_occurrences` и общий Today/календарь. `GET /api/tasks` возвращает ручные задачи; мутации источников через ручной Task API запрещены с 409. Привычки управляются своим модулем.

- `GET|POST /api/habits`, `GET|PUT|DELETE /api/habits/{id}`. Создание возвращает 201, удаление 204. GET по ID после удаления возвращает 404; история и статистика доступны владельцу отдельно. Вход `{title,description,tags,color,schedule,habit}`; PUT полностью заменяет шаблон. Общие лимиты текста/тегов/цвета соответствуют задачам. `schedule` обязателен и использует общий контракт. `habit={icon,sub_habits,reminder_enabled,reminder_minutes_before}`; значок 1–32 символа, подпривычки — до 50 объектов `{id:UUID,title,description}` со стабильными уникальными ID, названием 1–200 и Markdown до 20000 символов. `reminder_minutes_before=null` наследует настройку аккаунта, число — 0–1440. Напоминание требует времени в расписании. Список принимает `q` (название/описание) и точный `tag`.
- `POST /api/habits/{id}/marks/{date}` принимает `{status,completed_sub_habits:[],note:""}`; status `pending|completed|skipped|cancelled`, note — Markdown до 200000 символов. Будущие даты в зоне привычки запрещены. Подпункты должны принадлежать snapshot этого появления, без дубликатов. Для составной привычки `pending/completed` вычисляется по сумме отмеченных пунктов; `skipped/cancelled` — явное решение пользователя. API возвращает общее появление с `habit_mark={status,completed_sub_habits,note,marked_at}`; время ставит сервер. Task status проецируется в `todo/in_progress/completed/rejected`, но исходные skip/cancel различаются в `habit_mark`.
- `GET /api/habits/{id}/history` возвращает сохранённые появления с исходным текстом, пунктами, статусом, заметкой и временем. `GET /api/habits/{id}/statistics?from=...&to=...` — статистику одной привычки; `GET /api/habits/statistics?from=...&to=...` — рейтинг всех собственных, включая удалённые. Диапазон 1–366 включительных дат в зоне профиля.

Мутации привычек сериализуются существующей транзакционной блокировкой владельца. Повтор одинаковой отметки возвращает прежний snapshot и `marked_at`, без нового события. Любое реальное изменение отметки пишет `habit_marked`; создание, изменение и удаление — соответствующие доменные события. Текст личных заметок не копируется в payload события. Все маршруты требуют сессию, все мутации — Origin; чужой ID возвращает 404.

Правило версии: новая привычка может начинаться в прошлом, для внесения реальной истории. Изменение действует с текущей даты в зоне привычки, прошлые версии продолжают определять ожидаемые появления, включая неотмеченные. Несколько правок в один день заменяют версию этого дня. Сохранённая отметка всегда определяет snapshot своего появления, включая частичный результат; правка шаблона её не перезаписывает. Явная коррекция прошлого результата использует его исторические подпункты. Зона привычки после создания фиксирована; при необходимости смены создаётся новая привычка. Удаление прекращает появления со временем начала не раньше момента удаления; для правил без времени — с даты удаления в зоне привычки. Уже начавшиеся, в том числе просроченные в этот день, ожидания и все сделанные отметки сохраняются; результаты становятся неизменяемыми.

Статистика вычисляется сервером по версиям и реальным отметкам в диапазоне. Будущие даты исключены. `missed` — незавершённое появление до сегодняшней даты в зоне привычки либо после `starts_at + duration_minutes`; до этого оно `pending`. `skipped` — явный пропуск; `cancelled` исключается из процента и обеих серий. Процент = completed / (completed + skipped + missed), при нуле знаменателя 0. Серии считаются по плановым появлениям, дни отдыха исключены; текущее ожидающее появление не сбрасывает серию. Возвращаются expected/completed/skipped/cancelled/missed/pending, completed_sub_habits/total_sub_habits, completion_rate, current_streak/best_streak и longest_missed_streak/shortest_missed_streak/last_missed_streak. Все серии ограничены запрошенным диапазоном. Рейтинг сортируется по проценту, затем числу выполнений и названию.

`GET /api/reminders` возвращает массив `{task_id,date,title,starts_at,due_at}`. Сервер учитывает общий переключатель, текущую настройку привычки, срок start минус интервал, отсутствие результата/подтверждения и удаление. Напоминание доступно в течение 24 часов после due_at; при следующем открытии приложение получает ещё актуальные непрочитанные записи. `POST /api/reminders/{id}/{date}/dismiss` — идемпотентное подтверждение 204. Подтверждение относится к дате появления и не сбрасывается при правке шаблона. Доставка осуществляется при запросе из открытого приложения; фонового email/Web Push worker нет.

Проверка на реальных сервисах: `python3 scripts/habits_smoke.py`. Сценарий проверяет CRUD/поиск, изоляцию/CSRF, общие расписания, Today/календарь, сумму подпривычек, конкурирующие идемпотентные отметки, статистику/серии, исторические версии, удаление и напоминания.

## Интимный журнал (этап 6)

Миграция `0006_intimacy.sql` добавляет только `app.intimacy_entries`. Модуль `intimacy` обслуживает фактические события и собственную описательную статистику владельца. Общая аналитика и AI получают только отдельно разрешённую минимальную сводку. Журнал не создаёт задачи/привычки и не включается в общие поиск, Today, календарь или `activity_events`. Данные добровольные; API не делает медицинских выводов и не трактует отсутствие записей как воздержание.

Все маршруты требуют действующую сессию; мутации — прежнюю проверку Origin. Ответы `no-store`. Чужой UUID возвращает 404. JSON анкеты шифруется существующим AES-256-GCM с новым случайным nonce при записи и AAD `intimacy:v1:{user_id}:{entry_id}`; ciphertext нельзя переставить между записями или владельцами. В открытых метаданных БД остаются UUID, владелец, UTC `started_at`, revision и служебные даты. Ключ — существующий `DATA_ENCRYPTION_KEY`; замена без миграции делает и профили, и журнал нечитаемыми. Это серверное шифрование содержимого, сервер расшифровывает его для авторизованного просмотра и подсчёта. Приватные изображения используют общий медиа-контракт Garage, без отдельного шифрования файла.

### Маршруты

| Метод и путь | Контракт |
| --- | --- |
| `POST /api/sex` | Анкета EntryData → 201 Entry; сервер создаёт UUID. Несколько событий с одинаковым временем допустимы |
| `GET /api/sex/{id}` | 200 Entry владельца |
| `PUT /api/sex/{id}` | `{revision,data:EntryData}` → 200 Entry; полная явная коррекция, revision увеличивается |
| `DELETE /api/sex/{id}?revision=N` | 204; явное безвозвратное удаление анкеты |
| `GET /api/sex?from=YYYY-MM-DD&to=YYYY-MM-DD&kind=sex&offset=0` | Journal: `from,to,timezone,offset,limit,total,entries,statistics`. Обязательны from/to; kind необязателен (`sex`/`masturbation`), offset по умолчанию 0 |

Редактирование/удаление сериализованы блокировкой записи; устаревшая revision → 409 `stale_intimacy`, без изменения данных. Коррекции намеренно заменяют анкету, статистика пересчитывается; скрытая история чувствительных анкет не сохраняется. Удаление не оставляет копии в общей ленте событий. PostgreSQL/backups сохраняют обычные физические ограничения удаления. Общие медиа остаются отдельными приватными объектами: удаление анкеты не удаляет изображения, которые могут использоваться в других Markdown-описаниях.

Диапазон — 1–366 включительных дат в текущей IANA-зоне профиля, одинаковый для списка и статистики; offset 0–1000000, страница 50 записей, сортировка `started_at DESC,id DESC`. Статистика считается по всему выбранному диапазону/типу, независимо от страницы. Одна SQL-выборка зафиксированного набора записей служит источником обоих результатов. Для фильтра типа и агрегации сервер расшифровывает анкеты выбранного диапазона; шифрованное содержимое не индексируется. Пагинация по смещению: при конкурентном добавлении или изменении времени обновите журнал и начните с первой страницы.

### EntryData и время

Обязательны `kind` (`sex`/`masturbation`), `local_start` (ISO местная дата-время `2026-10-25T02:30:00`, строго до минуты), `timezone` (IANA). `time_occurrence`: `earlier` (по умолчанию) / `later` выбирает первое/второе вхождение повторяющегося часа. Несуществующее местное время отклоняется 400 `nonexistent_local_time`, без переноса фактического события. Начало — не раньше местного 1900-01-01 и не позже текущего серверного момента; это журнал, не расписание. Смена зоны профиля меняет группировку и отображение, сохраняя исходные момент/местное время/зону события.

Остальные поля необязательны, пропущенные измерения/ответы равны null, строки/списки — пустым значениям:

- `duration_minutes`: целое 1–1440 либо null; `ejaculation_count`: целое 0–100 либо null.
- `toys`, `emotions`: массивы строк; `lubricant_used`, `was_clothed`, `repeat_desired`: bool либо null. Ноль, false и неизвестный ответ различаются.
- `setting`: описание обстановки (Markdown, до 1000 символов); `note`: общий Markdown до 200000 символов.
- `partner`: объект либо null, только для `sex`. Поля `protection_used: bool|null`, `gender: ""|unspecified|female|male|other`, `name` (до 200), `positions` (список), `sex_types` (список из `anal,oral,vaginal,other`). Несколько видов поддерживаются; остальные поля партнёра добровольны.
- `solo`: объект либо null, только для `masturbation`. `porn_sources`: список произвольных названий/адресов (не загружаются сервером), `feelings_after`: Markdown до 5000 символов.

Каждый список: до 30 непустых пунктов по 500 символов, без внешних пробелов и повторов без учёта регистра. Неизвестные JSON-поля и несовместимые типу вложенные сведения отклоняются. Общие лимиты тела API остаются прежними.

Entry: `{id,started_at,data,revision,created_at,updated_at}`; `started_at` — вычисленный сервером UTC-момент, `data` содержит исходную анкету. Клиент не присылает чужого владельца или произвольный UTC-индекс.

### Описательная статистика

`total,sex,masturbation,active_days` — число событий/типов/дней с записями; `days` — карта дат текущей зоны профиля с количеством событий каждого типа. `duration_minutes,duration_answers,average_duration_minutes` учитывают только указанную длительность, среднее null при отсутствии ответов. `ejaculations,ejaculation_answers` сохраняют различие нуля и неизвестного. `with_toys` — число записей с явно перечисленными игрушками. `repeat_desired,lubricant_used,protection_used` содержат `{yes,no,unknown}`; защита считается только для `sex`. `emotions` — частота явно указанных эмоций без учёта регистра. Пустые дни не используются как измерение дисциплины или здоровья.

## Аналитика и удаление (этап 7)

Миграция `0007_analytics_deletion.sql` добавляет разрешения `analytics_privacy` и индексы выборки. Миграции 1–6 не меняются. Локальная аналитика не отправляет данные во внешние системы; разрешения AI управляются отдельно.

- `GET /api/analytics?from=YYYY-MM-DD&to=YYYY-MM-DD`: обязательный диапазон 1–366 дат включительно, годы 1900–9998. Неизвестные параметры и неверные даты возвращают JSON-ошибку 400. Ответ: `from,to,timezone,generated_at,privacy,event_count,active_days,event_types,tasks,habits,pomodoro,workouts,days` и только разрешённые `profile`/`intimacy`.
- `GET /api/analytics/privacy` → `{include_profile:false,include_intimacy:false}` по умолчанию. `PUT` принимает оба булевых поля и полностью заменяет разрешения текущего аккаунта. Неизвестные поля запрещены. Разрешения сохранены независимо от общих настроек; изменение настроек их не сбрасывает.
- Все API требуют сессию, PUT/DELETE — корректный Origin. Владелец определяется только сессией; чужой user_id нельзя передать. Ответы `no-store`, разрешения и отчёт не кэшируются. Сериализация отчёта/изменения разрешений через блокировку владельца не позволяет новому запросу использовать уже отозванное разрешение.

`event_count` и `event_types` агрегируют реальные activity_events только обычных модулей (notes/folders/tasks/habits/exercises/workouts/workout sessions/countdown/Pomodoro), по UTC occurred_at, переведённому в зону профиля. Создания, исправления, команды и удаления являются разными действиями; одинаковые идемпотентные отметки не дают новых событий. `active_days` — число дат с такими действиями. Это метрики использования приложения, не оценка дисциплины. Исторические типы прежних событий сохраняются. Payload, entity_id и содержимое объектов в отчёт не выдаются. `days` содержит каждую дату, включая нулевые дни.

Итоговые результаты считаются отдельно от событий:

- `tasks`: scheduled/completed/rejected/in_progress/pending/missed/future/planned_minutes/completion_rate по общим появлениям Today/календаря, только ручные задачи. Будущие даты профиля исключены из результатов. Просроченное без результата — дата раньше сегодняшней либо истёкшее starts_at + duration; для дедлайна без расписания — due_at. Процент = completed / (completed + rejected + missed); нулевой знаменатель → null. Плановые минуты не считаются фактически отработанными. Удалённые шаблоны дают только сохранённые результаты, без будущей генерации.
- `habits`: expected/completed/skipped/cancelled/missed/pending, суммы подпривычек и взвешенный completion_rate; используется прежняя общая логика версий/отметок/сроков, без второго движка. Отмена и ожидание исключены из знаменателя, отсутствие знаменателя → null. `ranking` — до 10 привычек с появлениями в диапазоне; порядок совпадает с разделом привычек. Серии ограничены диапазоном. Сводка учитывает все привычки, независимо от top 10.
- `pomodoro`: completed/cancelled и seconds только подтверждённых завершённых рабочих интервалов. Группировка по ended_at в зоне профиля; перерывы, активные, отменённые интервалы не дают времени фокуса. Паузы исключены серверным таймером.
- `workouts`: completed/partial/cancelled по ended_at, exercise_steps только подтверждённых упражнений (отдых исключён), фактические repetitions, seconds по сохранённым шагам плюс незавершённый сегмент остановленной сессии, без пауз. Время включает отдых. Результат тренировки и результат связанной привычки остаются отдельными метриками, не складываются как один показатель.

Задачи/привычки в динамике относятся к календарной дате появления (со временем — через starts_at и зону профиля), тренировки/Pomodoro — к дате завершения. Поэтому дата события исправления и дата результата могут отличаться. Изменение отметки пересчитывает итог, а не добавляет ещё одно выполнение.

`profile` отсутствует без include_profile; при разрешении сервер расшифровывает существующую анкету и возвращает только текущие age_years/height_cm/weight_kg, с null для неизвестного. Это текущий профиль, не история за период. Имя, контактные, социальные, медицинские и анатомические поля не выдаются. `intimacy` отсутствует без include_intimacy; при разрешении используется прежняя статистика журнала за диапазон, выдаются только total/sex/masturbation/active_days/duration_minutes/duration_answers/average_duration_minutes. Неизвестная длительность не входит в среднее. Имена, анкеты и тексты не возвращаются и не копируются в события. Отзыв не удаляет исходные данные, но исключает блок уже из следующего отчёта; явное удаление/коррекция анкеты сразу меняет сводку. Метрики описательные, без медицинских выводов.

### Физическое удаление

DELETE заметок/папок, задач, привычек, отсчётов, упражнений и планов физически удаляет строку из основной таблицы, возвращает 204; последующие GET/PUT/DELETE — 404. Отсутствуют текущие поля archived_at, операции восстановления и скрытые копии удалённых заметок. Интерфейс требует подтверждения. Папка оставляет заметки в корне; задача оставляет подзадачи в корне, ссылка Pomodoro становится null. Создание Pomodoro и удаление задачи сериализованы на владельца.

Используемое упражнение требует удаления ссылки из плана; план требует отвязать или удалить текущие привычки (иначе 409). Начатые/завершённые сессии содержат независимый snapshot и продолжают работать после удаления плана, упражнения или привычки. Завершение тренировки не восстанавливает удалённую привычку.

Исторические task_occurrences и habit_versions принадлежат пользователю независимо от существования шаблона. Для версий удалённой привычки ended_at ограничивает историческое расписание моментом удаления. Неначавшиеся появления и напоминания прекращаются, прошедшие ожидания и сделанные отметки сохраняются и недоступны для правки. История ручной задачи доступна по `/tasks/{id}/history`, если сохранились результаты; истории/статистика привычки — по прежним адресам. Чужая история возвращает 404. Календарь и рейтинг позволяют открыть сохранённые результаты удалённых объектов.

Миграция переводит прежние архивированные объекты в реально удалённые с сохранением результатов/версий/сессий. Файлы миграций 1–6 и тома сохраняются. Общие приватные изображения независимы и могут использоваться в других Markdown-описаниях; удаление заметки или шаблона не удаляет их. Обычные ограничения физического удаления из БД и резервных копий сохраняются.

Проверки: `python3 scripts/analytics_smoke.py --check-completion`, прежние smoke основных данных/привычек/тренировок/журнала, Chromium `frontend/e2e/analytics.spec.ts` и актуализированные сценарии удаления.

## AI и подключения

Миграции `0008_ai.sql` и `0009_ai_connections.sql` добавляют чаты, зашифрованные запросы/ответы/предпросмотры, независимые разрешения, отдельные ключи OpenAI/OpenRouter, регистрации ChatGPT и одноразовые OAuth-транзакции. Миграции 1–8 при продолжении не переписываются. Новая runtime-зависимость `jsonwebtoken` проверяет подпись и OIDC claims, тестовая `rsa` создаёт подписанные тестовые JWT; frontend новых зависимостей не требует.

- `GET/PUT /api/ai/settings`: revision, provider (`openai`/`openrouter`), auth_mode (`api_key`/`login`), model, enabled, permissions; `api_key`/`remove_key` относятся только к выбранному API-провайдеру. Старый клиент без provider/auth_mode сохраняет текущий выбор. Ответ содержит key_present, openai_key_present, openrouter_key_present, active_account_id и login_available, без секретов. Login поддерживается только с OpenAI.
- `GET/POST /api/ai/chats`, `GET/DELETE /api/ai/chats/{id}`: до 100 независимых чатов; удаление физически удаляет переписку и предпросмотры.
- `POST /api/ai/chats/{id}/preview`: revision, from, to, message и необязательный search (до 200 символов, фильтрует разрешённые задачи/заметки/библиотеку тренировок); возвращает точное тело внешнего запроса, срок пять минут и число предыдущих пар. Сеть провайдера не вызывается; предпросмотр доступен без подключения. Изменение настроек, подключения или чата делает его недействительным.
- `POST /api/ai/chats/{id}/messages`: preview_id и request_id UUID; 202 запускает фон, повтор того же идентификатора возвращает существующий результат без повторной отправки. `GET/DELETE /api/ai/chats/{chat}/messages/{id}` читает/останавливает запрос. Один ожидающий запрос на владельца, 5/минуту и 50/час через Redis независимо от удаления чата; 200 запросов/чат, 90 секунд на HTTPS inference. После прерывания нет автоматического повтора.
- `POST /api/ai/login/start`: revision и необязательный account_id для повторного входа; возвращает только внутренний URL. `GET /api/ai/login/authorize` проверяет исходную сессию и перенаправляет к OpenAI. `callback` принимает одноразовый state и authorization code; `complete` проверяет ту же LifeCycle-сессию и revision на исходном host перед сохранением подключения. OAuth не создаёт аккаунт LifeCycle и не заменяет вход по email.
- `GET /api/ai/accounts`: собственные регистрации, стабильные подписи, email из проверенного ID token и connected; токены/subject не возвращаются. `POST /api/ai/accounts/{id}` с revision выбирает сохранённый аккаунт; `DELETE` с revision очищает его токены и пытается отозвать refresh token. При обычном отключении регистрация и host ID сохраняются для повторного входа; дополнительное `forget:true` полностью удаляет регистрацию, включая отключённую. Host ID установки общий и не содержит данных аккаунта. Ответ remote_revoked=false требует отключить приложение в ChatGPT Settings; локальные токены уже удалены. До 10 регистраций на владельца.
- `GET /api/ai/models`: актуальный каталог активного ChatGPT-аккаунта (отдельный предел чтения 2 MiB), только visibility=list; для inference используется slug, а не подпись. Наличие модели в каталоге не означает успешную проверку inference.

OAuth реализован по [Registration and sign-in](https://developers.openai.com/siwc/token-sharing-open-source/sign-in), [Accounts and sessions](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions) и [Models and inference](https://developers.openai.com/siwc/token-sharing-open-source/models-and-inference). Локальный HTTP APP_PUBLIC_URL на localhost/127.0.0.1 использует callback `http://127.0.0.1:<APP_PORT>/api/ai/login/callback`; браузер должен работать на компьютере с LifeCycle. После callback браузер возвращается на исходный host для проверки исходной сессии. Удалённый/mобильный браузер не может использовать этот loopback-поток. Для удалённого сервера доступны API-ключи; веб-OAuth с произвольным callback требует отдельно одобренного OpenAI client и в этот контракт не входит.

Каждый вход использует PKCE S256, state, nonce и десятиминутную зашифрованную транзакцию. Первая регистрация использует dynamic_agent_client + LifeCycle + стабильный ext_agent_host_id; сохраняется выданный oaiapp client ID. Reauthorization проверяет прежний subject/client. Если после выдачи client ID обмен кода не завершился, сохраняется только неподтверждённая регистрация без identity/токенов; следующий вход повторно использует выданный ID и не разрешает inference до полной проверки. RS256/ES256, подпись OpenAI JWKS, issuer, audience, exp, iat и nonce проверяются до активации. Разрешение chatgpt.tokens.use.direct обязательно; identity-only вход не разрешает inference. Refresh сериализован блокировкой настроек, заменяет токены вместе; неопределённый или неудачный refresh требует повторного входа. Токены шифруются AES-GCM с владельцем/регистрацией и не попадают в browser storage или ответы API. OAuth callback query исключён из access log nginx; backend trace содержит только path. Уже выданный ID token допускается только в redirect id_token_hint на официальный authorize endpoint.

Внешние адреса фиксированы: OpenAI `https://api.openai.com/v1/responses`, OpenRouter `https://openrouter.ai/api/v1/responses`; произвольный base URL и автоматический fallback отсутствуют. Ключи никогда не переносятся между провайдерами. Вход ChatGPT использует только публичный API, store:false и stream:true, без max_output_tokens согласно [ограничениям потока](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations); успех только после response.completed. API-ключи используют JSON Responses с max_output_tokens=8192. OpenRouter дополнительно получает provider.data_collection=deny и provider.zdr=true; при отсутствии подходящего endpoint запрос завершается ошибкой. Это ограничивает доступные модели, включая некоторые бесплатные; не является обещанием бесплатности или полной анонимности. Данные получает OpenRouter и его поставщик модели. См. [Responses API](https://openrouter.ai/docs/api/reference/responses/overview) и [политику маршрутизации](https://openrouter.ai/docs/guides/routing/provider-selection).

Разрешения AI по умолчанию выключены и независимы от Analytics: числовая аналитика, ручные задачи/расписания, привычки с названиями, разрешённые тренировки, Markdown отмеченных заметок, полная анкета и минимальная интимная сводка. Контекст использует действующие `analytics::ai_report`, `tasks::occurrences`, профиль и интимную сводку. Максимум 366 дат; 100 появлений задач, 50 задач без расписания, 30 последних изменённых отмеченных заметок и до 4000 символов текста каждой. Тренировки ограничены 50 отмеченными планами/100 независимо отмеченными упражнениями/50 сессиями отмеченных планов. Ограничения явно включены в контекст. Изображения не скачиваются и не передаются; Markdown-ссылки остаются текстом. Сон отдельно не измеряется. История внешнего запроса — до 10 успешных пар той же revision. Смена провайдера, аккаунта, разрешений или настроек исключает прежнюю историю из новых запросов и отменяет ожидающие ответы; сохранённая владельцем переписка остаётся до явного удаления. AI предлагает изменения через ограниченный протокол приложения; запись требует отдельного подтверждения владельца, как описано ниже.

Шифрование серверное, не сквозное. Переданные провайдеру данные невозможно отозвать из LifeCycle. Тариф, разрешения и лимиты ChatGPT проверяет OpenAI; API-ключи оплачиваются по правилам соответствующего сервиса. Успешная локальная проверка OAuth-механики не заменяет настоящий пользовательский вход и завершённый ответ модели.

Для update существующих note/workout/exercise повторно проверяется доступ к источнику при подготовке и применении. Ссылка на существующее упражнение также должна быть разрешена; новое упражнение можно создать раньше в том же пакете.

Форма «Цели и персонализация» в AI, разрешение personalization и `/api/ai/preferences` удалены по запросу пользователя. Историческая зашифрованная таблица `ai_preferences` сохранена без чтения и передачи модели. Контекст строится из разрешённых разделов. Наследуемые поля permissions принимаются для совместимости старых клиентов, нормализуются и больше не выдаются. Общий поиск остаётся необязательным параметром preview API для совместимости; поля поиска в чате нет, доступ он не расширяет.

`GET/PUT /api/workouts/preferences` — цели и условия из раздела тренировок. Ответ/PUT: `{revision,data:{goals:string|null,equipment:string|null,restrictions:string|null}}`. Поля необязательны, до 2000 Unicode-символов каждое; пробелы обрезаются, пустое становится null (неизвестно). Хранение AES-GCM с привязкой к владельцу; чтение только своей записи. PUT проверяет сессию/Origin/revision, конфликт даёт `workout_preferences_stale` 409, одинаковое сохранение идемпотентно. Изменение увеличивает revision AI и инвалидирует прежние previews/ожидания/предложения/историю для новых запросов. Сохранённые данные включаются в `workouts.preferences` только с разрешением workouts. Старые `ai_preferences` не мигрируются автоматически в эти поля. AI не может редактировать условия или доступ. Ограничения — пользовательский текст для контекста, не автоматическая медицинская классификация.

Протокол предложений одинаков для поддерживаемых провайдеров: AI возвращает объяснение и fenced-блок `lifecycle-actions` с `{summary,actions}`. Пользовательский текст использует названия/даты, технические ID остаются в предложении. Контекст передаёт версии источников, измеренные результаты, пределы и усечение, до 100 связанных появлений при совместных workouts/habits. Явные skipped/cancelled отличаются от отсутствия сессии. Модель не выполняет HTTP/SQL и не расширяет права. Контекст/запрос ограничены 128/256 KiB.

`POST /api/ai/actions` с `{revision,source_turn_id?,summary,actions}` → 201 создаёт зашифрованное неизменяемое предложение на 15 минут. Summary 1–4000 символов; 1–20 действий, суммарно до 256 KiB. Action: `{entity:exercise|workout|task|note,operation:create|update,id:UUID,expected_updated_at:timestamp|null,data:object}`. Для create нужен новый ID, для update — точная текущая версия; data при update — частичный patch. Существующие записи с тем же нормализованным названием необходимо переиспользовать. Пробное выполнение всего пакета в SAVEPOINT использует общие транзакционные функции ручных редакторов и полностью откатывается. Подготовка не меняет сущности/события. Если source_turn_id задан, он должен принадлежать владельцу, быть completed и иметь текущую revision.

`GET /api/ai/actions?before=timestamp` возвращает последние 50 записей. `POST /api/ai/actions/{id}/apply` и `/undo` требуют `{confirmed:true}`; `/dismiss` отклоняет подготовленный пакет. Apply/undo атомарны и идемпотентны. Смена revision/TTL запрещает apply. Блокировки владельца/строк и before/after с updated_at защищают от параллельных правок. Undo доступен после отключения AI и отзыва доступа к объекту, сохраняет текущее состояние его AI-разрешения и отказывает при последующих правках или новых защищённых связях. Журнал переживает удаление чата, автоматически модели не передаётся; `activity_events` содержит ID/статус, без before/after.

Tasks/Notes используют общие проверки папок/родителей/иерархии/расписаний/истории; Today/календарь читают общую модель. Неизвестные поля, включая попытку выдать себе AI-доступ, отклоняются. AI не может удалять данные или менять права, профиль, провайдеры, интимные записи и Contacts. Новые заметки/тренировки/упражнения, в том числе созданные AI, тоже закрыты до отдельной отметки владельца.

Нагрузки и прогрессии проверяются существующим валидатором редактора. При известных состояниях/операциях/текущих лекарствах/беременности в профиле применение AI-нагрузки требует ручной проверки (`ai_safety_review_required`), без раскрытия личных полей в ошибке или передачи без разрешения. Отдельные ограничения из удалённой формы персонализации больше не применяются. Для повторений без таймера длительность заранее неизвестна.

### Ответы ChatGPT и проверка

Парсер собирает текст из `response.output_text.delta`, `response.output_text.done` и `response.output_item.done`, но завершает запрос только по явному `response.completed` со статусом completed. Финальный объект с полным output также поддерживается. При настоящей диагностике ChatGPT Login наблюдался completed с пустым output при корректных предшествующих текстовых событиях; раньше это давало ошибку неподдерживаемого ответа. Накопленный текст устраняет эту ошибку без повторной отправки запроса. Незавершённый/ошибочный поток по-прежнему не считается успешным. См. [официальное описание событий](https://developers.openai.com/api/docs/guides/streaming-responses). Предел SSE — 16 MiB, итогового текста — 256 KiB, JSON inference — 1 MiB; превышение даёт `ai_response_too_large`.

Полная приёмка: `python3 scripts/acceptance.py --url http://127.0.0.1:8081 --check-migrations --check-upgrade`. Upgrade/visibility smoke и Chromium используют Podman и `python3-cryptography` только для явно синтетических зашифрованных fixtures тестовых аккаунтов. Они проверяют владение, отзыв, фильтрацию контекста и аналитики, CAS, атомарность, версии, подтверждения и отмену. Внешний inference этими fixtures не подтверждается.

В запросе были только синтетическое задание и пустые источники заметок/тренировок. Предложение подготовлено без применения; временные чат/сессия/предложение удалены, личные записи не менялись.
